Everything in subtasks 1.1–1.10 is implemented: registration, login, browsing with search, filters and sorting, listing detail, offers, borrow requests and giveaway claims, chat, My Deals, profile, notifications, deal history, and rating and reviewing sellers. The app is Java 21 with JavaFX 21, built with Maven. All business rules live in a JavaFX-free service layer, so they are covered by unit tests. The UI only calls the services.

2. How to run

  • IntelliJ: open the folder as a Maven project (JDK 21+), then run hkust.marketplace.Launcher or Maven → Plugins → javafx → javafx:run.
  • Terminal: mvn javafx:run starts the app. mvn test runs the tests and writes the JaCoCo report to target/site/jacoco. mvn javadoc:javadoc builds the JavaDoc.
  • Demo buyer: demo_buyer / Buyer123. Data is saved to marketplace-data.ser; delete it to reset to the demo data.

3. Design

LayerResponsibility
modelSerializable entities (User → Buyer/Seller/Admin, Listing, Deal, ChatThread, Review, Notification, Report) and status enums. Shared with Tasks 2 and 3.
dataDataStore keeps every record and saves it to one file after each change. The write goes to a temp file and is then moved into place, so a crash never leaves a half-written file. SeedData creates the demo data.
serviceAll Task 1 rules, behind the Marketplace facade: AuthService, ProfileService, ListingService, ChatService, DealService, NotificationService, ReviewService. Each one checks the caller’s role and account status itself, not only the UI.
utilCredential rules, PBKDF2-HMAC-SHA256 salted password hashing (65,536 iterations), ids, and ValidationException, which carries every broken rule at once.
uiJavaFX screens and one shared stylesheet. A 1-second timer runs processDueDates() (reminders and auto-return) and refreshes the open page.
  • Concurrency: claim, accept and counter actions run inside synchronized(store), so two buyers claiming the same giveaway cannot both succeed. A unit test runs this with two threads.
  • Testable time: every service takes a java.time.Clock. Tests use a clock they can move forward, so reminders, auto-return and due dates are tested without waiting.
  • Deal lifecycle: Pending → Countered → Accepted/Borrowed → Completed/Returned/Auto-returned, or Declined/Withdrawn. When one buyer’s deal is accepted, the other open requests on that listing are declined automatically and their buyers notified.

4. Testing

There are 105 JUnit 5 tests in 11 test classes, one for every service plus the util, data and model classes. They cover normal flows, every validation message, role and ownership checks, boundary values, time-based behaviour and concurrency. Some examples:

  • A 4-second loan is rejected, while 5 seconds and the 1-minute start-time tolerance are accepted.
  • A price with 3 decimal places is rejected, while “12.000” is accepted.
  • Comments of 500 and 1,000 characters are accepted, and one character more is rejected.
  • The reminder is sent once, halfway through a short loan or 24 h before the end of a long one.
  • Auto-return leaves a listing the admin removed in the Removed state.
  • A corrupt or wrong-type data file is rejected, and a save failure is reported.

Coverage is measured with JaCoCo. The ui package, Launcher and MainApp are excluded (configured in pom.xml) because they need a display. They were tested manually, as the screenshots in section 6 show.

5. Assumptions and limitations

  • The Seller Portal (Task 2) and Admin Portal (Task 3) are done by teammates. Until they are merged, the seed data includes a counter-offer, an accepted claim and an active loan, so the buyer side of seller decisions can be shown. The seller rules (acceptDeal, declineDeal, counterOffer, counterBorrow) are already in DealService and unit tested, for Task 2 to reuse.
  • Passwords need at least 8 characters with an uppercase letter, a lowercase letter and a digit. Usernames are unique across all roles and case-insensitive.
  • Only listings that are Live, Reserved or Lent, from active sellers, are visible to buyers. Reserved and Lent listings can be viewed but not requested. The price filter applies to Sell listings only.
  • A buyer has at most one open (Pending or Countered) request per listing. Making a new one asks whether to replace the old one.
  • Data is stored locally in one serialized file. This is a single-machine desktop app, so there is no network or multi-user server. The listing photos in the demo data are generated placeholders.
  • A chat becomes read-only when the listing is removed or either account is deactivated. Chat history is never deleted.
